## 1. Goal

Point 21 adds a controlled technical Self-Healing layer to the Kings Logistics Automation Core.

The system may automatically repair only failures that have a clearly defined, low-risk and reversible recovery action. It never treats a successful workflow dispatch alone as proof of recovery: after the repair cycle, the complete technical health chain is run again and must still report a healthy system.

---

## 2. Automatic repair allowlist

Only three repair targets are permitted:

### Live Tracker / Statistics

Workflow: `live-tracker.yml`

Triggers include:

- overdue Live Tracker workflow
- failed Live Tracker workflow
- stale `data/live-tracker-snapshot.json`
- stale `data/statistics.json`

Safety budget:

- cooldown: 15 minutes
- maximum attempts: 2 per 120-minute window

### Driver Updates

Workflow: `driver-updates.yml`

Triggers include:

- overdue Driver Updates workflow
- failed Driver Updates workflow

Safety budget:

- cooldown: 15 minutes
- maximum attempts: 2 per 120-minute window

### Core Backup

Workflow: `core-backup.yml`

Triggers include:

- overdue Core Backup workflow
- failed Core Backup workflow

The automatic action is restricted to a normal backup. It does not perform an automatic restore.

Safety budget:

- cooldown: 60 minutes
- maximum attempts: 2 per 360-minute window

---

## 3. Explicitly blocked automatic actions

Point 21 does not automatically dispatch or mutate:

- Convoy live workflows
- HR workflows
- Staff workflows
- Management workflows
- Probation workflows
- personnel actions
- Discord member actions
- Discord role changes
- Discord permission changes
- kicks or bans
- automatic backup restore
- force pushes

Issues outside the strict repair allowlist remain manual-only and are escalated instead of guessed or force-repaired.

---

## 4. Loop and duplicate protection

Self-Healing uses persistent state in:

`data/self-healing-state.json`

For each safe repair target, the state tracks recent attempts and success/failure timestamps.

Protection includes:

- per-repair cooldowns
- limited repair attempts per time window
- 24-hour retained attempt history
- detection of recent queued/in-progress workflow runs
- no duplicate dispatch when a recent repair workflow is already active
- fail-closed behavior after the repair budget is exhausted

The persistent state ID set is verified against the exact repair allowlist.

---

## 5. Health-driven repair planning

The engine consumes `data/system-health.json` generated by the existing System Monitoring layer.

Issue IDs are mapped to safe repair targets only when explicitly configured. Unknown or higher-risk findings are never automatically converted into actions.

Possible cycle outcomes include:

- `healthy-no-action`
- `repairs-completed`
- `escalation-required`
- `no-safe-repair-available`

A repair cycle that cannot safely resolve an unhealthy condition exits non-zero so the problem stays visible.


1. Checkout the repository.
2. Run Point 21 syntax and safety tests.
3. Load the persistent Self-Healing state into an isolated temporary working file.
4. Build a fresh complete technical health snapshot.
5. Plan and execute only allowlisted safe repairs.
6. Refresh runtime state written by successfully recovered producer workflows.
7. Run the complete technical health checks again.
8. Process technical alert/recovery messages through the existing guarded System Alerts layer.
9. Run the Point 21 acceptance verifier.
10. Persist Self-Healing technical state using `scripts/git-safe-push.sh`.
11. Upload verification evidence.

## 10. Operational rule after Point 21

Self-Healing is a technical safety net, not permission to hide defects.

If a safe repair succeeds but the subsequent complete health check remains unhealthy, the issue remains open and is escalated. If a repair repeatedly fails, cooldown/budget protection stops the loop. If an issue requires HR, Staff, Management, Convoy, personnel, Discord role/member, restore or destructive Git action, Self-Healing does not perform it automatically.

Any future protected Core change supersedes the v1.1 fingerprint and requires a new successful Core baseline verification before becoming the accepted stable baseline.
